# Release note overrides

The release note published for each build is generated by the
`upstream-release.yml` workflow: it always contains the image tags, the
multi-arch digest, and the PHP version and image digest of every published
platform. Releases are tagged by build date (`2026.10.22`), and each
publication creates a new release.

Sometimes a release is not the usual "new upstream Observium version" release —
for example when the image is rebuilt because the PHP repository published a
new patch release for one architecture only. In that case you can override the
prose part of the release note.

## How to override

Create a file named after the Observium version, for example
`release-notes/26.1.14545.md`, with the reason in a front matter block:

```markdown
---
reason: Republished to pick up the arm64 build of PHP 8.5.12.
---

This release was rebuilt, not published for the first time.

- The `linux/arm64` image now carries the same PHP patch release as `linux/amd64`.
- The version tag was re-pointed at the rebuilt image.
```

The `reason` is **required**. The workflow fails the release job if an override
is present without one, because a release that deviates from the automated
path must state why.

The reason is rendered in the release as:

> **Why this release is not the usual automated one:** Republished to pick up the arm64 build of PHP 8.5.12.

The generated facts (tags, digests, PHP version per platform) are always
appended and cannot be overridden — they are read from the published image.

## Precedence

An override is resolved in this order:

1. the `workflow_dispatch` input — ad-hoc, for the run that is dispatched;
2. `release-notes/<observium-version>.md` — durable, reviewed in git.

The file is named after the Observium version (`26.1.14545`), not the build
date, so one file covers every build of that version. Since each publication
creates its own release, an override does not need to survive rebuilds — the
next build simply reads the same file again.

Delete the file (or empty it) and the next release note is the plain generated
one.

## Overriding at dispatch time

For an ad-hoc override, pass the same two values to a manual run:

```bash
gh workflow run upstream-release.yml \
  --ref main \
  -f release_notes="This image was rebuilt to pick up the arm64 PHP build." \
  -f release_notes_reason="Republished to pick up the arm64 build of PHP 8.5.12."
```

A dispatch input takes precedence over the file in this directory, but it is
not reviewable in git — commit the same text to
`release-notes/<observium-version>.md` so the reason is part of the repository
history.

## Rebuilding without a version change

`workflow_dispatch` always publishes, so a manual run re-builds the image and
adds a new date tag, plus a new release. The version tag moves with it. This is
also how the automated PHP refresh (`php-refresh.yml`) behaves.
